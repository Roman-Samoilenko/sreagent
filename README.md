Проект **SRE Agent** - это агент на LLM, ориентированный на решение задач SRE и DevOps. Он выполняет автоматический анализ сконфигурированных репозиториев, выявляет потенциальные проблемы в кодовой базе, фиксирует их в графовой базе знаний и использует векторное хранилище для накопления контекста. Агент работает в соответствии с ReAct-паттерном, самостоятельно выбирая и вызывая нужные инструменты, а все интеграции с внешними системами построены по принципам Model Context Protocol (MCP).

### Основные возможности и принцип работы

#### Анализ GitHub-репозиториев
Агент получает список репозиториев, заданный в конфигурационном файле. По запросу пользователя он способен выполнять следующие действия:
- **Просмотр содержимого директорий и файлов**: агент рекурсивно обходит дерево файлов с учётом списка исключённых директорий (например, `node_modules`, `vendor`, `.git`) и заданных расширений. Для каждого текстового файла он может запросить его полное содержимое, что необходимо для дальнейшего статического анализа.
- **Поиск по коду**: инструмент позволяет задать поисковый запрос (ключевые слова или выражения) и получить список файлов, в которых найдены совпадения. Это ускоряет поиск конкретных уязвимых шаблонов, устаревших вызовов или конфигурационных ошибок.
- **Работа с issues**: агент может выгружать список открытых, закрытых или всех issues, что даёт ему возможность учитывать уже зафиксированные проблемы и избегать дублирования.

Все эти операции реализованы через официальное API GitHub с использованием токена доступа, что гарантирует стабильность и безопасность взаимодействия. Агент не клонирует репозиторий локально, а взаимодействует с ним напрямую, что снижает требования к дисковому пространству и времени на анализ.

#### Графовая база знаний на Neo4j
Найденные в ходе анализа проблемы фиксируются в виде графа, отражающего отношения между сущностями. В графе присутствуют следующие типы узлов:
- **Repo** — репозиторий, представленный именем и при необходимости дополнительными атрибутами.
- **File** — файл, который принадлежит конкретному репозиторию (связь `CONTAINS`).
- **Bug** — описание найденной проблемы (уязвимости, ошибки, отклонения от лучших практик). Каждый баг привязан к файлу и репозиторию, имеет метку времени и текстовое описание.
- **Fix** — предложенное исправление (suggested fix). Связь `FIXED_BY` соединяет баг с соответствующим исправлением. Система автоматически привязывает исправление к последнему незакрытому багу в том же файле, что позволяет выстраивать цепочку «проблема – решение».
- **Report** — детальный отчёт, который может содержать более развёрнутый анализ, включая ссылки на сторонние источники, рекомендации и т.п. Отчёт связывается с конкретным багом через отношение `HAS_REPORT`.

#### Векторное хранилище Qdrant
Для работы с неструктурированной информацией и накопления контекста используется Qdrant — векторная база данных. Агент может:
- Добавлять документы (например, тексты предыдущих отчётов, выдержки из логов, сообщения об ошибках) в коллекцию, преобразуя их в эмбеддинги с помощью модели text-embedding-ada-002.
- Выполнять семантический поиск: по текстовому запросу возвращаются документы, наиболее близкие по смыслу, что позволяет агенту опираться на накопленный опыт при анализе новых инцидентов.
- Применять гибридные стратегии: сначала получить релевантный контекст из Qdrant, а затем передать его вместе с запросом модели, улучшая качество и обоснованность ответа.

Векторное хранилище выступает в роли долговременной памяти агента, компенсируя ограниченность краткосрочной памяти языковой модели.

#### ReAct-паттерн и принятие решений
Агент работает по циклу Reasoning and Acting (ReAct). Модель получает системный промпт, в котором перечислены доступные инструменты и требуемый формат ответа, и затем на каждом шаге генерирует рассуждение (Thought) и либо выбирает действие (Action) с конкретными аргументами, либо выдаёт финальный ответ (Final Answer).

#### Модель контекстного протокола (MCP)
Интеграция с внешними системами унифицирована через собственную облегчённую реализацию MCP. Каждый источник данных (GitHub, Neo4j, Qdrant) представлен как MCP-сервер, реализующий интерфейс `Server` с методами:
- `Name` — возвращает уникальное имя сервера.
- `ListTools` — возвращает список доступных инструментов с подробным описанием их входных параметров и возвращаемых значений.
- `CallTool` — вызывает конкретный инструмент с переданными аргументами и возвращает результат.

Специальный менеджер MCP (`Manager`) регистрирует все серверы, инициализирует их, собирает общий перечень инструментов и передаёт их в оркестратор в виде объектов, совместимых с LangChainGo. Это позволяет легко добавлять новые интеграции (например, Prometheus, Jira, Slack) без изменения ядра системы.

#### Краткосрочная и долговременная память
Помимо векторного хранилища, агент поддерживает краткосрочную память в рамках одной сессии. LangChainGo-исполнитель автоматически сохраняет историю диалога: запросы пользователя и ответы ассистента (включая промежуточные результаты вызова инструментов). Это даёт агенту возможность учитывать предыдущие реплики и не переспрашивать контекст.

### Компоненты приложения и их взаимодействие

- **App** (`internal/app`) — центральная точка сборки. В ней инициализируется LLM (через OpenRouter), создаются и регистрируются MCP-серверы, запускается оркестратор. App также управляет жизненным циклом приложения.
- **Orchestrator** (`internal/core`) — создаёт агента LangChainGo, подключает все инструменты, настраивает память и системный промпт, а затем обслуживает запросы пользователя, передавая их агенту и возвращая результат.
- **MCP-серверы** — изолированные модули, реализующие интеграции. Каждый сервер может быть запущен в одном процессе с агентом (in-process) или вынесен в отдельный микросервис (по необходимости).
- **Менеджер MCP** — отвечает за регистрацию серверов, обработку ошибок вызовов, логирование и предоставление единого списка инструментов оркестратору.
- **Инструменты** (`internal/tools`) — вспомогательные утилиты, такие как `list_configured_repos`, которые отдают агенту список репозиториев из конфигурации. Это сделано отдельным инструментом, чтобы агент мог динамически узнавать доступные для анализа репозитории, а не полагаться исключительно на промпт.
- **TUI** (`internal/tui`) — консольный интерфейс на базе библиотеки Bubble Tea, обеспечивающий интерактивное взаимодействие с агентом. Поддерживает прокрутку истории сообщений и одновременную работу с инструментами.
- **Updater** (`cmd/updater`) — демон-планировщик, который с заданным интервалом (например, раз в сутки) инициирует анализ всех сконфигурированных репозиториев, передавая агенту запрос на полную проверку безопасности. Результаты также фиксируются в графе знаний и могут быть опционально отправлены в Telegram.
- **Telegram-бот** (`cmd/bot`) — интерфейс для взаимодействия с агентом через мессенджер Telegram. Он принимает запросы от аутентифицированных пользователей, передаёт их агенту и возвращает ответы.

Все компоненты общаются через общий интерфейс оркестратора, что позволяет переключать пользовательские интерфейсы без изменения логики работы агента.

### Технологический стек и окружение

- **Язык программирования**: Go 1.26.5.
- **LLM-фреймворк**: LangChainGo (github.com/tmc/langchaingo) — предоставляет абстракции для построения цепочек вызовов, работы с памятью, агентами и инструментами.
- **LLM-провайдер**: OpenRouter (унифицированный доступ к множеству больших языковых моделей, включая бесплатные варианты, через OpenAI-совместимый API). Конкретная модель задаётся в конфигурации.
- **База знаний**: Neo4j 5.10.0 (графовая СУБД), доступ через официальный Go-драйвер.
- **Векторное хранилище**: Qdrant 1.4.0 (векторная база данных), взаимодействие через REST API с использованием клиентской библиотеки.
- **Протокол интеграций**: собственная реализация Model Context Protocol, инспирированная концепцией Anthropic, адаптированная для нужд проекта.
- **Пользовательские интерфейсы**: TUI на базе Bubble Tea (интерактивный терминальный клиент), демон-планировщик, Telegram-бот (библиотека для работы с Telegram Bot API).
- **Управление конфигурацией**: YAML-файл (основные настройки) и переменные окружения для секретов (токены, пароли). Используется библиотека godotenv для загрузки `.env`-файлов.
- **Контейнеризация и развёртывание**: Docker Compose — все сервисы (агент, Neo4j, Qdrant) запускаются в изолированных контейнерах, объединённых в одну сеть.
